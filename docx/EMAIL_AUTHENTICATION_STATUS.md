# AXION X — статус email-подтверждения и восстановления аккаунта

## Что найдено в исходниках

- `lib/auth.ts` конфигурирует Better Auth с email/паролем.
- `emailAndPassword.enabled` включён; минимальная длина пароля — 12 символов.
- `emailAndPassword.requireEmailVerification` не включён.
- `emailAndPassword.sendResetPassword` не настроен.
- В `components/auth/AuthPage.tsx` регистрация сразу вызывает `authClient.signUp.email(...)`; этапа отправки и проверки OTP нет.
- В `lib/auth-client.ts` не подключён клиентский Email OTP plugin.
- В коде и `.env.example` не найдено интеграции Resend или переменных `RESEND_*`.
- В Prisma есть `User.emailVerified` и стандартная модель `Verification`.
- В `MIGRATION_RECOVERY.md` упомянута ранее обнаруженная в Neon миграция `20261014000000_email_otp` и таблица `email_otp_challenge`, но соответствующего migration-файла в локальном `prisma/migrations/` нет. Существование записи в истории БД не доказывает, что актуальная схема приложения использует эту таблицу.

## Требуемый целевой сценарий

### Регистрация

1. Пользователь вводит имя, email, телефон и пароль.
2. Сервер проверяет формат и доступность email/телефона.
3. Отправляется шестизначный код на email.
4. Пользователь вводит код.
5. Сервер проверяет код, срок действия, количество попыток и привязку к email.
6. Только после успешной проверки создаётся пользовательская запись и продолжается вход.

Необходимо исключить создание аккаунта до подтверждения email. Нельзя доверять флагу подтверждения, который присылает браузер.

### Восстановление доступа

1. Пользователь вводит email.
2. Сервер отвечает нейтральным сообщением, не раскрывая наличие аккаунта.
3. Для существующего аккаунта отправляется шестизначный код.
4. Пользователь вводит код и новый пароль.
5. Сервер атомарно проверяет OTP и меняет пароль; после успешной смены нужно отозвать активные сессии.

Код должен иметь ограниченный срок жизни (например, 5 минут), ограничение попыток и частоты повторной отправки. Хранить OTP в открытом виде не следует. Повторное использование после успешной операции запрещается.

## Resend: требования к конфигурации

Для отправки нужен один выбранный Resend API key, который будет храниться только в серверной переменной `RESEND_API_KEY`, и подтверждённый домен отправителя. Адрес `RESEND_FROM_EMAIL` должен принадлежать домену, подтверждённому в том же аккаунте Resend, что и API key.

Не помещайте API key в `NEXT_PUBLIC_*`, исходники, Git, скриншоты или сообщения. Для локальной разработки добавляйте секреты в `.env.local`; для production — в Vercel Project → Settings → Environment Variables.

Два ключа от двух разных аккаунтов нельзя смешивать с доменами/отправителями другого аккаунта. Перед включением отправки необходимо выбрать аккаунт, в котором проверен домен отправителя, и проверить DNS-статус домена в Resend.

## Что требуется уточнить перед подключением реальной отправки

- Какой из двух аккаунтов Resend содержит подтверждённый домен отправителя для AXION X?
- Какой адрес отправителя планируется использовать (например, `no-reply@ваш-домен`)? Адрес должен быть на подтверждённом домене.
- Есть ли доступ к DNS этого домена, чтобы при необходимости добавить SPF/DKIM/DMARC-записи, предложенные Resend?

Сам API key в чат отправлять не нужно. Достаточно выбрать аккаунт и настроить секрет непосредственно в окружении проекта.

## Важное ограничение текущей итерации

Пока интеграция не подключена и не проверена реальной доставкой, регистрация и восстановление по email OTP не считаются реализованными. Наличие `emailVerified`, `Verification` или старой записи о миграции не является подтверждением работоспособности email-потока.
