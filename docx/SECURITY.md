# AXION X — меры безопасности аккаунтов и приложения

## Подтверждено текущими исходниками

- Better Auth хранит пользователей, сессии, учётные записи и verification records через Prisma/PostgreSQL.
- Минимальная длина пароля в серверной конфигурации — 12 символов, максимальная — 128.
- Телефон нормализуется и проверяется при создании пользователя; публичный ID генерируется на сервере.
- Включены ограничения частоты запросов Better Auth, в том числе для входа и регистрации.
- Для production включены secure cookies; cookie имеют `HttpOnly`, `SameSite=Lax`, `Secure` в production и `Path=/`.
- Роли и административные права должны повторно проверяться сервером по актуальной записи пользователя.
- Секреты не должны попадать в клиентский код, Git или архивы.

## Ограничения, которые нельзя считать закрытыми

- В текущем снимке не подключена отправка email через Resend.
- Обязательная проверка email через шестизначный OTP перед регистрацией не реализована.
- Самостоятельное восстановление пароля через email OTP не реализовано.
- `emailVerified` в схеме БД сам по себе не включает проверку email.

См. `EMAIL_AUTHENTICATION_STATUS.md`.

## Секреты и окружения

- Хранить `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BLOB_READ_WRITE_TOKEN`, VAPID private key и будущий `RESEND_API_KEY` только в серверном окружении.
- Не использовать префикс `NEXT_PUBLIC_` для секретов.
- Для Vercel задавать переменные отдельно для Development, Preview и Production.
- Не отправлять API keys и приватные ключи в чат, тикеты, GitHub или архивы.

## Перед production-релизом

1. Проверить права доступа к каждой административной API-операции.
2. Проверить rate limits и защиту OTP от перебора после внедрения email-потока.
3. Проверить сессии после смены пароля и выхода из аккаунта.
4. Проверить HTTPS, cookie flags, security headers и CORS/trusted origins.
5. Проверить резервное копирование PostgreSQL и миграции на staging.
