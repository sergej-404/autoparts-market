# AXION X 9.14.6 — диагностика холодного запуска

## Что изменено

- Популярные объявления главной страницы вынесены в отдельный `unstable_cache` с TTL 60 секунд и тегом `public-home-listings`.
- SQL-запросы популярных и новых объявлений выполняются только при заполнении/обновлении кеша, а не при каждом формировании главной страницы.
- Кеш главной страницы инвалидируется после административного изменения объявления и изменения остатков через операции с заказами.
- В `app/(home)/page.tsx` и `lib/public-catalog-data.ts` добавлены структурированные замеры времени. Они включаются только переменной `AXION_PERFORMANCE_DIAGNOSTICS=true` и не записывают персональные данные, SQL-параметры или содержимое объявлений.
- Кеширование справочников категорий и марок оставлено без изменений.

## Временное включение диагностики в Vercel

1. Открыть Vercel → Project → Settings → Environment Variables.
2. Добавить `AXION_PERFORMANCE_DIAGNOSTICS` со значением `true` для Production.
3. Выполнить новый Production Deployment.
4. После периода без посещений открыть главную страницу один раз, затем повторить запрос через 10–30 секунд.
5. В Vercel → Logs отфильтровать сообщения по `[AXION_PERF]`.
6. Сопоставить времена с длительностью Function Invocation и заголовками ответа `x-vercel-cache`, `age`, `x-vercel-id`.
7. После сбора нескольких холодных и тёплых запусков установить значение `false` или удалить переменную.

## События логирования

- `home.categories_cache` — получение кеша категорий.
- `home.popular_listings_cache` — получение кеша популярных объявлений.
- `home.makes_cache` — получение кеша марок.
- `home.data_ready` — суммарное время подготовки данных главной страницы.
- `home.listings.initial_queries` — длительность параллельных SQL-запросов новых объявлений и рейтинга избранного при заполнении кеша.
- `home.listings.favorite_details_query` — получение данных популярных объявлений при заполнении кеша.

Если `home.popular_listings_cache` занимает мало времени, а сама Function Invocation остаётся долгой, искать задержку нужно вне SQL-части главной страницы: холодный запуск функции, middleware/layout, авторизация или инфраструктурная сеть. Если медленные именно `initial_queries`/`favorite_details_query`, проверять пробуждение Neon, соединения и планы SQL.

## Настройка Neon / Prisma

Для Production Vercel следует проверить, что `DATABASE_URL` использует Neon pooled endpoint с hostname, содержащим `-pooler`, и параметром `connection_limit=1`. Не заменять строку целиком: сохранить текущие параметры `sslmode`, `channel_binding` и прочие обязательные параметры, добавив `connection_limit=1` через `&` либо `?` в зависимости от наличия query string.

Изменение выполнять в Vercel Environment Variables, а не в Git. После изменения — redeploy и smoke test авторизации, главной страницы, каталога, заказов и чатов. В этом коммите Production-переменные окружения и локальные секреты не изменялись.

## Ограничения проверки

В среде подготовки архива `npm ci` не завершилась в отведённое время, поэтому полноценные `type-check`, ESLint и Next.js production build пока не подтверждены. Production Vercel и Neon недоступны из этой среды; холодный запуск должен быть измерен после публикации.
