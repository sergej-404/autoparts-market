# AXION X — меры безопасности аккаунтов

## Что включено в проект

- Серверная проверка сессии для разделов администратора и модератора.
- Роль проверяется повторно по текущей записи пользователя в PostgreSQL; роль из клиентского запроса не используется для авторизации.
- Неизвестные значения роли трактуются как отсутствие доступа.
- Better Auth ограничивает частоту запросов глобально и отдельно для входа, регистрации и операций сброса пароля.
- Минимальная длина пароля на сервере — 12 символов; максимальная — 128. Ограничение также отражено в форме регистрации.
- Secure/HttpOnly cookie-настройки для production, SameSite=Lax.
- HTTP security headers, отключён `X-Powered-By`; HSTS включается только в production.
- Секреты и `.env` не должны попадать в git или архивы проекта.

## Обязательные настройки перед production

1. Используйте только HTTPS и задайте точные production-адреса в `BETTER_AUTH_URL`, `NEXT_PUBLIC_APP_URL` и при необходимости `ADDITIONAL_TRUSTED_ORIGINS` (список через запятую). Не добавляйте произвольные домены.
2. Сгенерируйте уникальный `BETTER_AUTH_SECRET` длиной не менее 32 случайных символов. Храните его в менеджере секретов хостинга, не в репозитории.
3. Используйте отдельную production-базу PostgreSQL с TLS, минимальными правами DB-пользователя и регулярными резервными копиями. Ограничьте сетевой доступ к БД.
4. Настройте распределённое хранилище rate-limit (например, Redis через поддерживаемый Better Auth storage/plugin) перед горизонтальным масштабированием. Лимиты, хранящиеся только в памяти одного процесса, не защищают между несколькими инстансами.
5. Настройте и протестируйте доставку email, подтверждение адреса, восстановление пароля и уведомления о смене важных данных до включения соответствующих потоков в production.
6. Проведите проверку зависимостей (`npm audit` с анализом результатов), тесты контроля доступа и проверку конфигурации хостинга.
7. Назначайте `ADMIN`/`MODERATOR` только доверенным способом на серверной стороне или непосредственно в БД с аудитом. Не добавляйте поле роли в пользовательские формы/API.
8. Настройте мониторинг неуспешных входов, подозрительных сессий, ошибок авторизации и доступ к журналам только уполномоченным сотрудникам. Не записывайте пароли, токены или секреты в логи.

## Важно

Это усиление базового слоя безопасности, а не гарантия абсолютной защиты. Перед запуском с реальными пользовательскими данными необходимы интеграционные тесты на целевой платформе, проверка потоков email/восстановления пароля, аудит всех будущих API-маршрутов и независимый security review. Одной проверки страницы недостаточно: каждый API endpoint и каждая операция с данными должны отдельно проверять сессию, роль и принадлежность ресурса.
