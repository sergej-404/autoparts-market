# AXION X 9.14.3 — отчёт о реализации оптимизаций

Дата: 2026-11-09

## Область проверки

Проверен архив `AXION_X_9_14_3_AUDIT_STAGE_2.zip`. В архиве 175 файлов исходного проекта. Сверены версии зависимостей по `package-lock.json`:
- Next.js 16.4.5
- React 19.2.0
- TypeScript 5.9.3
- Prisma и Prisma Client 6.19.3

Секретные файлы окружения в исходном архиве отсутствуют. Фактические Production-переменные Vercel и логи Neon/Vercel в архив не входят.

## Подтверждённые результаты аудита

- PrismaClient создаётся централизованно в `lib/prisma.ts`; другие вызовы `new PrismaClient()` в TypeScript/TSX исходниках не обнаружены.
- Маршрутов с `runtime = "edge"` не обнаружено. API с Prisma по умолчанию работают в Node.js; один маршрут заказов явно задаёт `runtime = "nodejs"`.
- До изменений не было `unstable_cache` и сегментного ISR.
- Главная страница выполняла запросы к категориям, маркам, избранным событиям и объявлениям при регенерации страницы.
- Страница каталога и `/api/catalog` получали все публичные объявления без `take`/пагинации; клиент выполнял фильтрацию массива.
- В `app/api/admin/listings/route.ts` проверка совместимости могла выполнять последовательные запросы к БД внутри цикла — до двух запросов на одну запись совместимости (лимит входного списка 500).

## Реализованные изменения

### 1. Кеширование публичных справочников

Добавлен `lib/public-catalog-data.ts`:
- категории кешируются на 3600 секунд;
- марки для главной страницы кешируются на 3600 секунд;
- марки вместе с моделями для каталога кешируются на 3600 секунд;
- кеши имеют теги `public-catalog-categories` и `public-catalog-makes`.

Кеши используются на главной странице, странице каталога и в публичном API каталога. Изменение справочников через `app/api/admin/catalog/route.ts` инвалидирует соответствующие теги.

### 2. ISR главной страницы

В `app/(home)/page.tsx` добавлено `export const revalidate = 60`.

Это позволяет отдавать ранее сформированную страницу между регенерациями вместо выполнения полного набора запросов при каждом обращении. При изменении объявлений и остатков добавлена инвалидация главной страницы.

### 3. Устранение N+1 при проверке совместимости объявлений

В `app/api/admin/listings/route.ts` проверки марок и моделей для списка совместимости заменены на две пакетные выборки `findMany` с `in`, после которых проверка соответствия выполняется в памяти.

Ограничение списка в 500 записей и проверки корректности марки, модели и года сохранены.

### 4. Инвалидация ISR после изменения данных

В `app/api/admin/listings/route.ts`, `app/api/orders/route.ts`, `app/api/orders/[orderId]/route.ts` и `app/api/admin/orders/route.ts` добавлен вызов `revalidatePath("/")` после успешного изменения объявлений или остатков.

### 5. Документирование конфигурации Neon

В `.env.example` добавлено напоминание: для Production Vercel следует использовать pooled hostname Neon (`-pooler`) и `connection_limit=1`.

Фактический `DATABASE_URL` Production не предоставлен, поэтому его значение не изменялось и наличие pooler не подтверждено.

### 6. Снижение лишней нагрузки от счётчиков шапки

В `components/layout/Header.tsx` периодический запрос `/api/chat/unread` изменён с интервала 10 секунд на 30 секунд. Обновление при первом отображении, возврате фокуса, открытии вкладки и событиях приложения сохранено. Добавлена защита от параллельных одинаковых запросов, чтобы одновременные события `focus`/`visibilitychange` и таймер не создавали дублирующую нагрузку. Последние известные значения счётчиков сохраняются при временной сетевой ошибке.

Это уменьшает фоновую частоту обращений к авторизации и Neon примерно втрое на одну открытую активную вкладку; счётчики по-прежнему обновляются сразу после внутренних событий приложения и при возвращении пользователя на вкладку.

### 7. Проверка Vercel Blob

Существующая загрузка фотографий уже использует прямую клиентскую загрузку через `@vercel/blob/client`, публичный Blob, уникальные UUID-пути, ограничение 8 МБ, JPEG/PNG/WebP и `cacheControlMaxAge` 30 дней. Это подходящая схема для публичных фотографий объявлений: браузер получает изображения с Blob/CDN, а не через функции приложения. Конфигурация изображений Next.js разрешает соответствующий Blob hostname.

Маршрут `/api/admin/upload/verify` после загрузки повторно скачивает изображение в функцию и проверяет MIME и сигнатуру файла. Это дополнительный сетевой запрос и расход трафика при загрузке, но он выполняет серверную проверку содержимого; удалять эту проверку ради ускорения без замены на равноценную проверку небезопасно. Схему хранения и URL существующих фотографий не менял.

## Что намеренно не менялось

- Prisma schema и SQL migrations.
- Данные Neon и тестовые записи.
- Логика резервирования остатков и транзакции заказов.
- Публичные контракты API.
- `maxDuration`: не увеличивался без Production-логов и подтверждения тарифных лимитов.
- Vercel Blob: текущая прямая клиентская загрузка и публичная CDN-доставка сохранены; формат URL и хранилище не менялись.
- Edge Runtime: массовых изменений не требовалось.
- Пагинация каталога: требует отдельного изменения клиентского интерфейса, серверной фильтрации и сортировки. Простое ограничение выборки скрыло бы часть объявлений, поэтому оно не добавлялось.
- Production DATABASE_URL и секреты.

## Проверки

- Синтаксическая транспиляция TypeScript/TSX для изменённых файлов предыдущего этапа была успешной.
- Изменённый `components/layout/Header.tsx` дополнительно проверен на синтаксическую транспиляцию глобальным TypeScript: успешно.
- Изменения конфигурации `.env.example` проверены вручную.
- `npm ci --ignore-scripts --no-audit --no-fund`: не завершилась за 200 секунд в доступной среде; полноценная установка зависимостей не состоялась.
- `npm run type-check`, ESLint, Prisma validate/generate и Next.js build: не выполнены, поскольку зависимости не установлены.
- Подключение к Neon, Production smoke test и анализ логов Vercel: не выполнены.

## Обязательные действия перед Production-релизом

1. В Vercel → Project → Settings → Environment Variables проверить `DATABASE_URL` для Production: pooled hostname с `-pooler` и `connection_limit=1`. Не публиковать полное значение.
2. Проверить логи Functions и Neon за период зависаний: `P2024`, `FUNCTION_INVOCATION_TIMEOUT`, `too many connections`, connection reset/refused, query timeout.
3. После успешной установки зависимостей выполнить `npm run type-check`, `npm run lint`, `npx prisma validate`, `npx prisma generate`, `npm run build`.
4. Проверить главную страницу, каталог, создание/редактирование справочников, создание заказа и отмену заказа.
5. Сравнить TTFB главной страницы и каталога до/после развёртывания; отдельно проверить первый запрос после длительного простоя.

## Вывод

Реализованы безопасное кеширование справочников, ISR главной страницы, инвалидация кеша после изменений и устранение подтверждённого N+1 в проверке совместимости объявлений. Эти изменения сокращают повторные обращения к Neon и позволяют обслуживать главную страницу из кеша между регенерациями.

Нельзя утверждать, что исходная Production-проблема полностью устранена: Production URL, логи и фактическое время холодного запуска недоступны, а полная сборка не была выполнена из-за невозможности установить зависимости в среде проверки.
