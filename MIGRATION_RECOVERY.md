- Архив `AXION_X_9_14_3` от 09.11.2026 содержит 22 локальные SQL-миграции.
- В Neon применены ещё пять миграций, оригинальные SQL-файлы которых отсутствуют локально: `20261014000000_email_otp`, `20261019000000_add_admin_system_data`, `20261019010000_remove_seeded_demo_data`, `20261019020000_add_user_public_id`, `20261029150000_partner_program`.

- Сообщение `migrate status: Database schema is up to date!` **не** означает отсутствие drift при `migrate dev`.

## Текущее состояние архива на 09.11.2026

В архиве присутствуют 22 локальные SQL-миграции. Пять миграций из списка выше по-прежнему отсутствуют в локальной папке. Диагностический SQL в `prisma/inspect-neon.sql` предназначен только для чтения и дополнительно проверяет наличие записей этих миграций в `_prisma_migrations`.

На этапе аудита 09.11.2026 `schema.prisma` и SQL-миграции не изменялись. В API внесены только проверки диапазона PostgreSQL `INTEGER` для цен, количеств и итогов заказа, а также защита возврата зарезервированного остатка от переполнения. Эти изменения не требуют миграции БД.

## Проверки, которые безопасно проводить сейчас

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\check-migration-files.ps1
npx prisma validate
npx prisma migrate status
npx prisma migrate diff --from-schema-datamodel prisma/schema.prisma --to-schema-datasource prisma/schema.prisma --exit-code
```

Последняя команда может завершиться кодом 2: это значит, что обнаружено различие; такой результат ожидаем до восстановления истории. SQL в `prisma/inspect-neon.sql` только читает состояние БД.

## Реальный путь исправления **без потери данных**

1. В Neon создайте ветку-копию текущей базы и убедитесь, что резервная копия доступна. Не используйте `migrate reset`, `db push --force-reset`, ручное редактирование `_prisma_migrations`.
2. Получите SQL-файлы отсутствующих миграций из старых резервных копий / других компьютеров или архивов. Из SHA-256 восстановить оригинальный SQL нельзя. Восстановление оригинальных файлов — самый безопасный путь.
3. Если архивов не существует, спроектируйте новую **baseline-историю для новой базы** отдельно от существующей истории Neon. Снимите DDL и структуру данных ветки-копии; восстановите постмиграционные эффекты старых SQL/data migrations отдельно. Не утверждайте, что baseline тождественен утраченным SQL-миграциям.
4. Для развертывания с нуля проверьте новый baseline на **пустой тестовой базе** (проверки всех таблиц, индексов, ограничений, enum, FK и дефолтов). Для текущей Neon согласуйте переход в **тестовой ветке** и только после подтверждения отсутствия потерь примите отдельный план для production.
5. Запустите `npx prisma generate`, `npm run type-check`, `npm run build` и интеграционные сценарии заказов/чатов с копией данных.

## Важно

Этот пакет **не является окончательным исправлением drift** на основной Neon: в переданных файлах нет пяти исходных SQL-миграций, а к живой БД здесь нет подключения. Создание фиктивных миграций или изменение checksums сделало бы состояние хуже. Запускать `migrate dev` на основной Neon до исправления истории не следует. Для текущего деплоя `prisma migrate deploy` тоже не применять без отдельного тестирования полной истории.
