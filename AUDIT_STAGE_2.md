# AXION X 9.14.3 — этап 2: целостность числовых данных и миграции

Дата: 09.11.2026

## Исправления в коде

### 1. Диапазоны PostgreSQL INTEGER

Prisma-поля `Listing.price`, `Listing.quantity`, `Order.total`, `OrderItem.unitPrice`, `OrderItem.quantity` и `OrderItem.lineTotal` хранятся в PostgreSQL `INTEGER`, диапазон которого ограничен `-2_147_483_648..2_147_483_647`.

Ранее серверная проверка цены и количества использовала `Number.isSafeInteger`. Это проверяет точность JavaScript, но допускает числа, которые не помещаются в PostgreSQL `INTEGER`. Такие значения могли приводить к ошибке Prisma/БД вместо контролируемого ответа валидации.

Теперь:
- создание и редактирование объявления ограничивают цену и количество диапазоном `0..2_147_483_647`;
- создание заказа проверяет `lineTotal` каждой позиции и общую сумму до записи в БД;
- переполнение суммы возвращает контролируемую ошибку `400`.

### 2. Защита восстановления остатка

При отмене заказа зарезервированный остаток возвращается условным `updateMany`, который допускает увеличение только если итоговое значение не превысит `2_147_483_647`.

Если объявление существует, но возврат привёл бы к переполнению, транзакция откатывается, статус заказа не меняется, API возвращает `409`. Отсутствующее объявление продолжает обрабатываться отдельной ошибкой.

### 3. Безопасная диагностика истории миграций

`prisma/inspect-neon.sql` теперь:
- показывает статусы записей `_prisma_migrations`;
- отдельно проверяет пять миграций, отсутствующих в локальном архиве;
- показывает список таблиц и приблизительное число строк из `pg_stat_user_tables`;
- выполняет точный подсчёт строк только для существующих таблиц, не прерывая весь скрипт из-за отсутствующей legacy-таблицы.

Скрипт только читает данные. Он не меняет схему, строки или `_prisma_migrations`.

## Следующий обязательный шаг для восстановления миграций

1. Создать отдельную Neon branch от Production.
2. В SQL Editor именно этой ветки выполнить `prisma/inspect-neon.sql`.
3. Сохранить вывод по пяти migration records, таблицам и legacy-данным.
4. Сверить checksums отсутствующих локально миграций с резервными копиями/другими архивами.
5. Не запускать `migrate dev`, `migrate deploy`, `db push` или reset на Production до согласованного плана восстановления.
