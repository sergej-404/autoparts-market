# AXION X 6.9 — аудит подготовки к Production

Этот файл фиксирует фактическое состояние проекта по исходникам архива `AXION_X_9_14_2`. Неподключённые внешние сервисы и бизнес-правила не подменяются предположениями.

## Выполнено в текущей итерации

- Загрузка фотографий объявлений переведена с локальной файловой системы Vercel на Vercel Blob Client Uploads.
- Токен загрузки выдаётся только после серверной проверки роли `ADMIN`.
- Сохранены лимиты: JPEG/PNG/WebP, максимум 8 МБ на файл и 10 фотографий на объявление.
- После загрузки сервер проверяет MIME, размер и сигнатуру файла; неподходящий файл удаляется из Blob.
- В `Listing.images` по-прежнему хранятся строки URL; изменение схемы БД для Blob не требуется.
- Старые `/uploads/...` исключены из отображения; добавлена миграция очистки таких ссылок с сохранением валидных Blob URL.
- Счётчики сообщений и уведомлений получают актуальные значения одним запросом. Обновление по событиям сохранено; резервная проверка выполняется только для видимой вкладки.
- Главная страница ограничивает выборку товаров.
- Sitemap включает страницы доступных товаров; для страницы товара формируются индивидуальные SEO-метаданные.

## Фактические ограничения текущей бизнес-логики

1. Проект описан как магазин одного продавца. Оформление заказа создаёт заявку и резервирует остаток товара в транзакции. Администратор вручную подтверждает заказ; отмена возвращает остаток.
2. В модели получения есть только самовывоз и встреча в указанном покупателем месте. Интеграции службы доставки в коде не обнаружено.
3. Платёжный провайдер и онлайн-оплата в коде не обнаружены. Текущий сценарий не является автоматической оплатой заказа.
4. В README зафиксировано, что подтверждение email и самостоятельное восстановление пароля пока не включены.
5. В каталоге отображаются фильтры скидки и рейтинга, но в модели `Listing` нет соответствующих полей и текущая фильтрация их не применяет. Сортировка по рейтингу также не имеет источника данных. Не следует имитировать эти значения.
6. Страница каталога и `/api/catalog` загружают все доступные объявления. Для крупного каталога требуется отдельный этап серверной фильтрации и пагинации; простое ограничение `take` без интерфейса продолжения скрыло бы часть товаров.
7. Фотографии сообщений заказа передаются как data URL и хранятся в JSON-поле PostgreSQL. Это отдельный поток от фотографий объявлений; при росте переписки его стоит перевести на объектное хранилище и ограничить суммарный размер.
8. Email-провайдер в окружении не равен реализованной email-рассылке: в исходниках не найден вызов Resend для писем о заказах/регистрации.

## Наблюдаемость и производительность

- `DATABASE_URL` в предоставленном окружении указывает на Neon pooled endpoint; секреты из `.env` и `.env.local` не должны попадать в репозиторий или публичный архив.
- Регион Vercel Function `fra1` и регион Neon `eu-central-1` находятся в одной географической зоне; явного межконтинентального маршрута по этим данным не видно.
- Медленные первые запросы сами по себе ещё не доказывают проблему Neon Scale-to-Zero. Для вывода нужны Runtime Logs и метрики Neon в момент воспроизведения задержки.
- Папка PWA содержит `manifest.webmanifest`; единичный `ERR_CONNECTION_RESET` не доказывает отсутствие файла.

## Требует решения до подключения платёжного и логистического контуров

- Платёжный провайдер и режим: оплата на сайте, платёжная ссылка после подтверждения или только оплата при получении.
- География продаж и служба доставки; текущая форма рассчитана на российский номер `+7` и цены в RUB.
- Политика возвратов, гарантий, обработки персональных данных и публичные юридические страницы.

Эти решения влияют на модели заказов, переходы статусов, вебхуки и возврат остатков. Они не должны внедряться путём добавления случайного платёжного API или фиктивных статусов.
